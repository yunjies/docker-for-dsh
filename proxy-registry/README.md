# Reverse-proxy registration service

This service lets the DSH container register its reachable Docker-host IP, published web port, and launch token without SSH from the container to the proxy. It runs on the reverse-proxy host, binds only to `127.0.0.1:13833`, and is exposed through the existing TLS Nginx listener at `/_internal/dsh/register`. Nginx forwards the client source address; the service requires that address and the submitted upstream IP both match the configured Docker-host IP, plus a Bearer credential.

On accepted registration, the service calls a sudo-restricted root helper. The helper updates the Nginx upstream and invokes the existing `/usr/local/sbin/dsh-update-token-map 13832` script with the token on stdin. The registration record is stored at `/var/lib/dsh-token-registry/registration.json` with mode `0600`. Neither the service nor helper logs request bodies or tokens.

The systemd unit uses `ProtectHome=read-only` because this proxy's Nginx TLS certificate chain is stored under `/home`; `nginx -t` must read that chain while the privileged helper validates a candidate config. `ProtectHome=true` hides the certificate path inside the service sandbox. Do not set `ProtectSystem=full` or `RestrictAddressFamilies`: their sandboxing can set `NoNewPrivileges`/`nosuid` and prevent the service's narrowly permitted `sudo` helper from elevating. The API binds only to loopback and validates the forwarded source IP; the service account remains unprivileged and sudoers permits only the fixed helper command.

## Install on the proxy host

The installer is specific to a proxy host whose Nginx configuration has a DSH server block at `/etc/nginx/conf.d/deepseek-harness-13832.conf` and the existing token updater at `/usr/local/sbin/dsh-update-token-map`. It verifies the current config shape, backs up the server block and any pre-existing upstream include under `/etc/nginx/.dsh-token-registry-backup`, adds the API location and named upstream, validates with `nginx -t`, and reloads Nginx. Do not run it on another host without first adapting and reviewing those paths.

Prepare a random Bearer credential on the Docker host and keep its file outside the repository with mode `0600`. Copy this directory to a temporary staging directory on the proxy host, then invoke `install-proxy.sh` as root with `DSH_REGISTRY_ALLOWED_SOURCE_IP` set to the Docker host address. Supply the same credential file on stdin; do not put the credential in command arguments, shell history, or environment variables. The installer stores it root-owned and readable only by the service group. The service account is unprivileged; sudoers permits it to invoke only the fixed registration helper with no arguments.

Set `DSH_PROXY_API_HOST`, `DSH_PROXY_API_IP`, `DSH_PROXY_REGISTRATION_URL`, `DSH_PROXY_REGISTRATION_SECRET_FILE`, and `DSH_PROXY_UPSTREAM_IP` in the DSH deployment's private `.env`. The API URL must use a hostname covered by the proxy's TLS certificate; Compose maps that hostname to the proxy's LAN IP. `DSH_PROXY_UPSTREAM_IP` must be the same host address from which Nginx sees the registration request. Compose sends its published `DSH_WEB_HOST_PORT`; the service records and routes to that IP/port. The installer restricts registrations to the currently configured web port. If the Compose host port changes, update `DSH_REGISTRY_ALLOWED_WEB_PORT` in `/etc/dsh-token-registry/config` on the proxy and restart the service before starting the changed container.

The API can be checked without changing the active token map by sending an invalid or unauthenticated request and confirming a `4xx` response. Do not use a valid test token against the live service unless you intend to replace the current launch token and upstream.
